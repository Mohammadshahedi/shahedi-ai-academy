# راهنمای عملیات فاز ۳B.2 و آمادگی ۳B.۳

## بازبینی آمادگی زیر ۱۸ سال

- صفحه `/admin/minor-readiness/` فقط برای حساب فعال دارای نقش `ADMIN` و `guardian_links.review` قابل مشاهده است.
- این صفحه فقط وضعیت را نشان می‌دهد؛ هیچ موردی را تکمیل، تأیید یا فعال نمی‌کند.
- وضعیت `READY` هویت مدیریت‌شده به معنی مجازبودن دریافت داده کودک نیست؛ وضعیت کلی تا رفع همه موانع `BLOCKED` می‌ماند.
- مدیر نباید متن حقوقی، مدرک سرپرستی، نام یا مشخصات کودک را در GitHub، issue، audit یا یادداشت عملیاتی وارد کند.
- پس از دریافت تصمیم‌های رسمی، فعال‌سازی باید در یک فاز مستقل با migration افزایشی، بازبینی امنیت و آزمون منفی انجام شود.

## راه‌اندازی مدیر نخست

1. یک secret تصادفی حداقل ۳۲ نویسه‌ای را فقط در runtime Sites با نام `ACADEMY_BOOTSTRAP_SECRET` تنظیم کنید.
2. با حساب بزرگسال مالک وارد `/admin/bootstrap/` شوید و secret را یک‌بار وارد کنید.
3. پس از موفقیت، secret را از runtime حذف کنید؛ رکورد `admin_bootstrap_state` استفاده دوباره را رد می‌کند.
4. نقش `ADMIN` و permissionها صریح هستند؛ وجود نقش به‌تنهایی دسترسی ایجاد نمی‌کند.

هیچ secret، ایمیل، شناسه هویت یا داده واقعی را در GitHub، issue، log یا این سند ثبت نکنید.

## دعوت کارکنان

1. مدیر دارای `staff_invitations.manage` ایمیل تأییدشده و نقش مدرس/مدیر را در `/admin/` وارد می‌کند.
2. token خام فقط یک‌بار در پاسخ خصوصی نمایش داده می‌شود و باید از کانال امن خارج از سامانه تحویل شود.
3. دعوت‌شده با همان ایمیل تأییدشده Sites وارد `/staff-invitation/` می‌شود.
4. دعوت پس از ۲۴ ساعت، لغو، پذیرش موفق یا replay رد می‌شود.

آکادمی در این فاز provider ارسال ایمیل ندارد و نباید ارسال خودکار را ادعا کند.

## تعلیق و دسترسی

- تعلیق، عملیات حساس حساب را فوراً متوقف می‌کند.
- مدیر نمی‌تواند وضعیت، نقش یا permission خودش را تغییر دهد.
- آخرین مدیر فعال یا آخرین دارنده permission حیاتی `accounts.roles.manage` قابل‌حذف نیست.
- هر mutation از origin، action header، rate limit، حساب فعال و permission تازه عبور می‌کند.

## حذف و نگهداری

- کاربر می‌تواند درخواست حذف را ثبت یا لغو کند.
- `ACCOUNT_PURGE_ENABLED` تا تصویب نسخه نگهداری داده `false` است.
- جدول `retention_policy_versions` عمداً بدون seed است؛ تعداد روزها نباید حدس زده شود.
- تکمیل حذف باید بعداً به نسخه سیاست فعال، audit و امکان بازیابی مصوب متصل شود.

## پاسخ رخداد

1. حساب مشکوک را تعلیق و دعوت‌های باز مرتبط را لغو کنید.
2. permission و نقش‌های فعال را بازبینی کنید؛ payload یا PII را در audit دستی ننویسید.
3. زمان، action code، target داخلی و request ID را ثبت کنید.
4. دامنه اثر و الزام اطلاع‌رسانی را با مسئول حقوقی/حریم خصوصی بررسی کنید.
5. پس از اصلاح، حساب را فقط با تصمیم ثبت‌شده فعال کنید.

## rollback

- rollback کد می‌تواند به Commit فاز ۳B.1 برگردد؛ migration `0001` حذف یا بازنویسی نمی‌شود.
- جدول‌ها و ستون‌های افزوده‌شده در rollback کد بلااستفاده می‌مانند و داده حذف نمی‌شود.
- دعوت‌های باز پیش از rollback باید لغو شوند.
- rollback برش readiness فقط صفحه، لینک و validator ۳B.۳ را حذف می‌کند؛ چون schema و داده‌ای اضافه نشده، rollback داده ندارد.
- Force Push ممنوع است؛ rollback با Commit جدید و آزمون migration انجام می‌شود.
